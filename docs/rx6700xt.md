## Test log

The next section is updated from actual runs, including launch mode, peak
private memory, frame rate, loading stalls, shader failures and crashes.

### Initial safe-mode run (2026-11-25 22:52)

Command profile: upstream `scripts/play.ps1 -Safe` on the real RX 6700 XT.

- Boot, intro and menus: mostly 30 fps.
- Reached the game world without an out-of-memory error or crash.
- Peak sampled private memory: 23.7 GiB. The 31.6 GiB machine therefore has
  headroom, but little room for unrelated applications.
- World preparation produced 190 to 9,128 draws per frame and fell to 0-3 fps
  while pipelines and streamed data were prepared.
- The log contains no `ERROR` entries.
- Startup logged 29 unimplemented pipeline-creation slots and one dropped
  dispatch. These can omit effects or draws and need comparison against the fast
  profile.
- `scripts/play.ps1` passed the literal value `none` to
  `VICTORY_SKIP_PIPELINES`, which expects shader hashes. This produced a warning
  and did nothing useful.

The safe profile is a useful compatibility baseline, but it is not the profile
we want for play. It confirms that the full data set and this GPU can enter the
world on a 32 GiB machine.

## Changes made for this machine

1. Registered the supplied `1.0.2.1` Scarlett executable by BLAKE3 in
   `KNOWN_BUILDS`, so `victory.exe` no longer reports it as an unknown build.
2. Removed the invalid `VICTORY_SKIP_PIPELINES=none` default from the upstream
   play script.
3. Added `scripts/play-rx6700xt.ps1`:
   - detects physical and logical CPU counts;
   - gives the translator and joined submissions work matched to the six
     physical cores instead of the 7900 XTX machine's eight-core split;
   - keeps four mapping workers as the maximum on this CPU;
   - caps shadow-side card buffers at 2 GiB on the 12 GiB GPU;
   - defaults to the fast path and keeps `-Safe` for diagnosis.
4. Kept the game cache and saves in an isolated data tree under
   `victory-data-6700xt`.

### First threaded/fast run (2026-11-25 22:57)

The first RX 6700 XT profile used six translator threads, six joined
submission parts, four mapping workers, a 2 GiB card-shadow cap and the
upstream fast-path relay settings.

- Menus stayed at 29-32 fps.
- The build was identified correctly as `1.0.2.1 retail (Scarlett)`.
- Peak sampled private memory was 17.6 GiB before the world transition; the
  later world samples reached 22.7 GiB.
- The world transition fell to 1 fps with 336-1,527 draws per frame.
- The GPU device was removed with `0x887A0007` six seconds after the world
  became active, while eight pipeline-making threads were compiling shaders.
- Breadcrumbs were empty and no RAM commit refusal was logged.

The fork's public issue history explains this: RX 6900 XT, 6950 XT and 6750 XT
reports remove the device with relay stages 1/2; `RELAY=0` survives. Texture
no-wait and the extra object-retirement lag have independent device-loss
reports. The 7900 XTX path is therefore not safe as the default for this card.

## Stable RDNA 2 profile

`scripts/play-rx6700xt.ps1` now defaults to a stable profile:

- `VICTORY_RELAY=0`
- `VICTORY_TEXTURE_NO_WAIT=0`
- `VICTORY_CARD_STEPS=0`
- `VICTORY_BURY_LAG=0`
- `SHOW_AFTER=1`, keeping the upload-order device-loss fix
- six translator threads and six joined submission parts
- 2 GiB shadow-side card-buffer ceiling

The upstream 7900 XTX speed path remains available explicitly with
`-ExperimentalFast`. It is not the default until it completes a long session on
RX 6700 XT hardware.

### Stable profile run in progress (2026-11-25 23:00)

The default profile reports `profile=stable physicalCores=6 logicalCpus=12
translateThreads=6 joinParts=6 mappingThreads=4`.

- Menus remained at 30-32 fps.
- The world became active after about 95 seconds.
- The opening world cell ran at 1-5 fps with 679-6,383 draws per frame.
- Private memory settled around 23.4-24.4 GiB. It stopped climbing in the
  sampled window instead of approaching the 31.6 GiB limit.
- At 23:04:41 the process was still responsive, with no `ERROR`, device-removal,
  out-of-memory or watchdog line in the stable log.

This is already materially different from the fast profile, which removed the
device six seconds after the world became active.
